Architecture

The codebase is organised to separate concerns cleanly:

automata-lab/
├── css/style.css — complete design system & all components
├── js/
│ ├── algorithms/nfaToDfa.js — pure subset construction algorithm
│ ├── validators/nfaValidator.js — input validation, returns error list
│ ├── utils/stateSetUtils.js — set operations (union, canonical label)
│ ├── data/examples.js — pre-built NFA configurations
│ ├── data/simulatorRegistry.js — all 15 module definitions
│ └── components/layout.js — shared navbar, footer, theme system
├── index.html — landing page
├── dashboard.html — module dashboard
├── simulator.html — NFA→DFA simulator workspace
├── learning.html — theory & worked examples
└── about.html — this page

The algorithm (nfaToDfa.js) is a pure function — it has no DOM dependencies and can be tested independently. The simulator page imports it and wires it to the UI.

Algorithm Correctness

The subset construction implementation has been manually verified against the assignment example:

✓ Input NFA (q0,q1,q2) over {0,1} produces exactly 4 DFA states: {q0}, {q0,q1}, {q0,q2}, {q0,q1,q2}.
✓ Accepting states correctly identified as {q0,q2} and {q0,q1,q2} (contain q2).
✓ No dead state needed (all transitions defined).
✓ Canonical state labels (always sorted) prevent duplicate states.

Edge cases handled:

  • Missing NFA transitions → dead state ∅ added to DFA
  • Multiple NFA transitions for same symbol → union computed correctly
  • Unreachable NFA states → never appear in DFA (BFS only visits reachable subsets)
  • Self-loops → handled naturally by the algorithm
  • Empty string input → checked against initial DFA state directly
  • Invalid symbol in test string → rejected with error message
